# MCP tools contract

## Purpose

Expose read, retrieval, status, lint, and controlled write operations to coding agents over MCP stdio.

## Function signatures

```js
/** @param {{config:Config,paths:ResolvedPaths,env:object}} options @returns {McpServer} */
export function createServer(options);
/** @returns {Promise<void>} */
export function main();
```

## Input

Tool schemas are: `wiki_query{query:string,limit?:number,compact?:boolean,provenance?:boolean}`, `wiki_read_page{path:string,anchor?:string,maxChars?:number}`, `wiki_read_index{}`, `wiki_list_pages{type?:string}`, `wiki_status{}`, `wiki_lint{}`, `wiki_write_page{path:string,content:string,expectedSha256?:string}`, `wiki_update_page{path:string,content?:string,patch?:object,expectedSha256?:string}`, `wiki_create_entity{name:string,content:string}`, `wiki_create_concept{name:string,content:string}`, `wiki_add_crosslinks{path:string}`, and `wiki_update_index{}`.

## Output and errors

`wiki_update_page` with `patch` accepts only the keys `frontmatter` (an object, merged into the existing frontmatter), `body` (a string, replaces the body) and `append` (a string, added to the end of the body). `body` and `append` may be given together: the body is replaced first and the appended text is then added to it. Any other key (own keys only; a `__proto__` key counts as unknown), a `patch` that is not a plain object, a non-object `frontmatter` (including one with a `__proto__` key), or a non-string `body` or `append` returns `E_INVALID_INPUT` with a fixed message that does not echo the caller's values; nothing is written and nothing is logged. When `content` is also given, `content` takes precedence, but `patch` is still validated.

`wiki_update_index` returns `{indexed, added, removed}`: `indexed` is the number of pages on disk, `added` the number of pages that gained an entry line, and `removed` the number of entry lines removed. When `wiki/index.md` exists and is non-empty, it is edited minimally: every existing line is kept byte for byte (summaries, tags, notes, paragraphs, headings and line endings). Entry lines anywhere in the file (including above the first heading) whose local `.md` target no longer exists are removed; external and anchor-only links are never removed. A local target's `#fragment` and `?query` are ignored for matching and removal, so `entities/ali.md#ozet` links `entities/ali.md`, and `entities/gone.md#x` is removed when that page is gone. Lines inside fenced code blocks (``` or ~~~) are opaque: they are never counted, removed, or used as headings or insertion points. Link destinations are read the way CommonMark reads them: `\(` and `\)` are escaped parentheses, and balanced unescaped parentheses also belong to the destination. A page counts as linked if any entry line anywhere in the file points to it, so it is not listed twice. A new entry writes parentheses in the path escaped (`entities/a\(b\).md`). A path that contains a space, a tab, a C0 or C1 control character or DEL (other than the line breaks above) is written as an angle-bracket destination (`<entities/my note.md>`, with parentheses still escaped inside, e.g. `<entities/a \(b\).md>`), because a plain destination would not end as a link; the reader accepts both forms, and a page is linked whichever form names it. Each page without an entry gets one line `- [Title](path) — summary #tag` placed after the last entry of its category (`## <folder>`, matched case-insensitively). A page at the Wiki root uses the category `## Pages`; a missing category is appended at the end of the file (a file that ends inside an open fence is closed first). Note: the vendored `readIndex` does not unescape link destinations and misreads unescaped balanced parentheses, so it must not be used to parse index lines this server writes. The summary comes from frontmatter `summary` or `description`, and the tags from frontmatter `tags` that are word-like. The link text (title) and the summary are line-safe: every run of whitespace or control characters (C0, C1 and DEL, which includes CR, LF, U+0085, U+2028 and U+2029) becomes one space, and the text is trimmed. A title that is empty after this falls back to the file name without `.md`, so an entry line is never split by its label. Pages are listed without following symlinks, so a symlinked page or directory is never indexed or read into the index. A page whose path contains a carriage return, a line feed, U+0085, U+2028 or U+2029 is never written to the index, because a line break would split or corrupt the entry line. Other control characters (C0, C1 and DEL) and tabs are allowed: such a path is written inside angle brackets and reads back exactly. Such a page stays in `wiki_list_pages` and `pageCount`, is not added by `wiki_update_index` or `wiki_create_*`, and is not counted in `indexCoveragePct`. Existing lines for it are kept as they are. When the index is missing or empty, it is rebuilt from the page frontmatter in the same format: escaped destinations, one `## <first folder>` category per folder, root pages under `## Pages`, entries sorted by path. The content is scanned for secrets before the write.

`wiki_create_entity` and `wiki_create_concept` add the new page's line through the same minimal edit, limited to that page: with an existing index, only the new entry line is inserted under its folder's category (matched case-insensitively, so `## Entities` receives an `entities/` page), and no other line is removed or changed; stale entries are left for `wiki_update_index`. Without an index, a fresh index with that one entry is written in the same format. The secret scan runs on the full index text before any write, so a refusal changes nothing. A name with no letter or digit left after transliteration (an empty slug) is refused with `E_INVALID_INPUT` before anything is written, so no page with an empty slug (such as a hidden `.md` file) is created. Turkish and accented Latin letters in a name are transliterated to ASCII before the slug is formed (`Deneme Varlık` → `deneme-varlik`).

`wiki_status` `indexCoveragePct` is the rounded share of countable Wiki pages (0 to 100; 100 when there are none, including the empty-Wiki view for a `wiki/` directory that resolves outside the vault) whose path an entry line of `wiki/index.md` links, read with the same parser as `wiki_update_index`; a missing index gives 0. The other `wiki_status` fields are unchanged.

`wiki_read_page` also returns `sha256`: the lowercase hex SHA-256 of the file bytes on disk, computed over the whole file even when `content` is truncated. Read tools take no lock.

Section read and compact query (BA-32): `wiki_read_page{path,anchor?,maxChars?}` may name one section. The path may end in `#fragment`, which is then the anchor; a leading `#` on `anchor` is ignored, a conflict between the two or an empty anchor is `E_INVALID_INPUT`. The body is the file text without its frontmatter, split exactly as the index loads pages, and the section whose anchor matches is returned as `{path,anchor,heading,headingPath,content,truncated,sha256}` (`content` is the section text). An unknown anchor is `E_INVALID_INPUT: Unknown anchor.` and no page text appears in an error. `maxChars` is an integer 1–20000 (`E_INVALID_INPUT` otherwise); `content` is cut with `prefixKeepingPairs` and `truncated` is true when a cut happened. Without an anchor, `content` is the whole file cut to `min(maxChars,20000)`. Without `anchor` and `maxChars` (and without `#` in the path) the response is unchanged. `wiki_query{query,limit?,compact?}` with `compact:true` drops only the `snippet` key of every result, on the lexical and the hybrid path; other keys, values and order, and the top-level keys, are unchanged.

Low-confidence pull results (BA-53): low-confidence rows are returned by default; only an explicit `retrieval.pullLowConfidence: false` turns them off. Unless the key is `false`, a lexical abstention whose `reason` is `below_threshold` returns the below-threshold rows instead of an empty list. The response becomes `{results:[…],abstained:true,lowConfidence:true}`, where every row gains `lowConfidence:true` as its last key (and still loses `snippet` with `compact:true`); `abstained` stays `true`. When the search returns no rows, or the reason is `identifier-not-found`, `no_match` or `empty-query`, the response is the unchanged abstained response. Non-abstained answers never carry `lowConfidence`. With the key `false` every response is byte-identical to before. The same flag makes the tool description add one sentence about `lowConfidence` rows; with the key `false` the description is unchanged. The flag applies to the pull path only and does not change hook output.

Synthesized sections (BA-57): on the lexical path a row from a synthesized section carries `synthesized: true` unchanged (the row mapping never drops unknown keys; `compact` still removes only `snippet`), and a verified page's `trust` is omitted for that row. On the hybrid path the flag comes from the section object chosen for the row (the lexical row of the query, otherwise `bestSection` on the page body, otherwise the chunk section): `synthesized: true` is added to its section fields and a `trust: 'verified'` is dropped from that row. A chunk-only heading has no section object, so such a row is never flagged (limit: the hybrid path marks only rows whose chosen section is a marked block). `weak` stays `weak` and the ranking is unchanged. See the retrieval contract, "Synthesized sections".

Write tools: `wiki_write_page` and `wiki_update_page` accept an optional `expectedSha256` (64 hex digits; any other value is `E_INVALID_INPUT`). When it is given, the current bytes of the page are hashed inside the write lock. A different hash, or a missing page, returns `E_CONFLICT` with a fixed message that echoes neither content nor hash; a refused call changes no file and writes no log record. A successful write returns `sha256` of the bytes written, only when `expectedSha256` was given; without it the response and behaviour are unchanged from before.

Provenance on write (BA-63, BA-74): `wiki_create_entity`/`wiki_create_concept`, and `wiki_write_page` when it creates a page, add `generated` (UTC timestamp of the write) to the page frontmatter when the content has no such key. Replacing an existing page — `wiki_write_page`, or `wiki_update_page` with `content` — does not fake freshness: content that carries `generated` keeps it as given; content without it keeps the existing page's non-empty `generated` value byte for byte; when neither has one, nothing is added. They never add `status`: a `proposed` stamp would turn a neutral page into a weak one that ranks lower and is marked `[unverified]`, so the author sets `status` (BA-69). Fields the author supplied are never changed, and evidence fields (`sources`, `verified`, `stale_after`) are never invented. A page written with `content` replaces the old frontmatter, so a previous `status: confirmed` is gone unless the new content carries it; the SHA-256 returned by the write is the one to pass as `expectedSha256` next, because the stored bytes differ from the content the client sent. `wiki_update_page` with `patch` keeps the existing frontmatter and adds nothing. Existing pages are not migrated. `wiki_query` with `provenance: true` adds `provenance: none|partial|full` to each result row (how many of `generated`, `status`, `sources`, `verified`, `stale_after` the page has; empty values such as `sources: []` do not count); without it the rows are unchanged.

Concurrency: every Wiki write (pages, `index.md`, `log.md`, crosslinks, creates) runs under one vault-wide lock file `wiki/.brainatlas-write.lock`, created with `wx` and holding `{pid, time, token}`. A holder releases it only while its token is still in the file. A lock is taken over when its pid is no longer running, or when it is older than 30 seconds. A live, fresh lock is waited for in short steps for up to 5 seconds; then the call fails with `E_BUSY` and nothing is written. The lock file is hidden and not a `.md` file, so page listings, status and search never count it, and the Wiki tools refuse it as a path (`E_PATH_ESCAPE`). Pages, `index.md` and `log.md` are replaced by renaming a temporary file in the same folder, so a reader sees either the old or the new version. Caveats: the lock file lives in the synced vault, so a sync client may show it briefly; `wiki_add_crosslinks` still writes its linked pages through the vendored core non-atomically, though under the same lock.

Read tools return bounded page/index/status/lint data. `wiki_query` first calls the searcher's `refreshIfChanged()`, so pages added, edited, deleted or renamed outside this server process (Obsidian, sync, another agent's MCP server) are returned by the next call; when semantic retrieval is enabled, such a change also schedules a background semantic index update. Write tools are omitted from the advertised tool list when `config.readOnly` is true. Before every write, content is passed to `scanText`; findings fail with `E_SECRET_DETECTED` and matched secret values are never returned. Invalid paths return `E_PATH_ESCAPE`. When the Wiki directory `wiki/` itself resolves outside the vault's real path, `wiki_read_page`, `wiki_read_index`, `wiki_lint` and `wiki_update_index` return `E_PATH_ESCAPE`, while `wiki_list_pages`, `wiki_status` and `wiki_query` answer as an empty Wiki (no pages, no results, no outside content). A vault root that is itself a symlink is allowed, because the comparison uses the real path of the vault.

## Example

```js
await client.callTool({name:'wiki_query',arguments:{query:'decision log',limit:3}});
```

## Security

Validate relative paths, scan all proposed write content, and avoid returning full content in diagnostics. Read-only mode must not advertise write tools.

## Version

Tool names and schemas above are version 1. Server and stdio signatures are fixed in `packages/mcp/src/index.mjs`.

When semantic retrieval is enabled for the configured module, `wiki_query` adds `semantic:{used:boolean,fallbackReason?:string}` and `mode:lexical|semantic-primary|rrf`. Missing modules or manifests report `module-missing`; module loading failures report `module-load-error`. Provider errors, absent indexes and fingerprint mismatches also fall back to lexical results. An empty index is missing when the vault contains pages. With semantic disabled or excluded from the configured modules the original response shape is preserved. Semantic index updates run in the background after writes or an index miss. In hybrid results (`semantic.used:true`) the order is the semantic module's order, unchanged: RRF order in `rrf` mode, and cosine order (then lexical rank, lexical-only hits last) in `semantic-primary` mode. `score` is the value of that ordering: `rrfScore` in `rrf` mode, and `semanticScore` in `semantic-primary` mode (0 for a lexical-only hit). `rrfScore` is always present in hybrid results; `semanticScore` is present when the hit has a cosine value. Section fields (`heading`, `anchor`, `headingPath`) follow the core anchor rule (diacritic folding, `-N` suffixes for repeated headings, astral characters dropped) and are chosen in this order: the lexical section of this query when the page is in the lexical answer; otherwise the core section for the query on the page body (`bestSection` with the query terms, the choice the core makes for that page); otherwise the section of the chunk text, used only when its headingPath equals the chunk's; otherwise `anchor` is null and `heading` is the chunk's heading. The snippet comes from the semantic chunk and the section fields come from the core, so a snippet and its heading can come from different sections. `snippet` is cut to the character budget without splitting a surrogate pair. `stale` uses the core `stale()` rule.
