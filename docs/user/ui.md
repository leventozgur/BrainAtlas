# Local panel (`brainatlas ui`)

> **Experimental.** The local panel is an experimental convenience and may change between releases.

`brainatlas ui [--no-open] [--json]` starts a small local web panel and prints its URL. Stop it with Ctrl+C, or let it close itself after 30 minutes without a request; it then prints `BrainAtlas panel closed after 30 minutes idle.` and exits with status 0.

- It listens on `127.0.0.1` only, on a random port. The printed URL carries the per-run token in the fragment (`/#t=<token>`), which the browser never sends to the server; the page reads it from `location.hash`, removes it from the address bar and sends it as the `x-brainatlas-token` header on every API call. Requests with a foreign `Host` or `Origin` are refused.
- On a shared machine, use `--no-open`: the opened URL is visible to other local users in the process list.
- The panel shows the status summary (same data as `status --summary`), agent channels and the editable scalar settings.
- Settings are typed controls derived from the configuration schema, never a second copy of it: an enum is a select, a boolean a checkbox, an integer or number a number input with its minimum, maximum and step, and any other string a text field. Every row carries a one-line description, and a value that differs from the profile default shows `Reset`. `Apply` stays disabled while the control still holds the current value (or an empty or out-of-range number), so an unchanged row cannot be applied.
- The server stays authoritative: a value of the wrong JSON type, outside the min/max range or not in the enum is refused with HTTP 400 `E_CONFIG_INVALID` and a short message naming the key and the allowed values or range, and nothing is written.
- Every change asks for confirmation and shows what it will change: `Apply`, `Reset` and `Install` first request a plan from the same code as `config set`, `agent set` and `agent add`, show it in a confirmation dialog, and only `Confirm` writes. The dialog names the change in plain text, for example `hooks.mode: "normal" → "economic"`, `kiro: MCP server → CLI + skill` or `Install kiro with CLI + skill`, then lists the semantic check steps, the warnings and the files the plan would change (`Files:` and one path per line). The raw plan JSON stays available under a small `Raw plan` disclosure.
- An installed agent shows its channel select and `Apply`; `Apply` stays disabled while the selected channel equals the current channel. An agent that is detected but not installed shows a channel select and `Install`. Visible channel names are `MCP server` and `CLI + skill` (the status line reads e.g. `channel CLI + skill (healthy)`); the stored values stay `mcp` and `cli`. The tooltips explain each channel: MCP means the agent calls BrainAtlas tools over MCP, CLI + skill means the agent runs the `brainatlas` CLI guided by an installed skill file.
- In the Lite profile, or when the installed release does not ship the semantic module, the `semantic.*` rows are hidden and the panel shows `Semantic search needs the Full profile and release. See docs/user/semantic.md.`; a semantic key is then refused with HTTP 400 `E_CONFIG_KEY`. The panel never changes the profile, because switching to the Full profile needs the Full release archive; that stays a CLI and installer operation (`brainatlas init --profile full`, or installing a Full release).
- Turning `semantic.enabled` on first runs the same in-process check as `brainatlas semanticSetup --dry-run --json`. If a step reports `action-needed`, the panel shows the reasons and the `next` command and writes nothing (HTTP 409 `E_SEMANTIC_NOT_READY`). Otherwise the plan lists the check steps, its RAM and disk warnings and the fixed note that each prompt waits up to 350 ms for semantic search. The dry run never downloads a model, pulls or indexes; turning the switch off needs no check.
- Paths, interpreter, state location, sync transport options, channels, agents and modules cannot be edited from the panel. In a read-only installation all changes are disabled (HTTP 403).
- Output is redacted, and the vault path and token are never shown in the page data.
